# Форма заявки в техподдержку МИС

Одностраничная форма: заявитель заполняет поля, прикладывает **до 10 файлов по 100 МБ**,
жмёт «Отправить». Файлы уходят на Яндекс.Диск техподдержки, текст заявки — письмом
в Planfix (`RomanFigol@sensey.planfix.ru`).

**Заявителю никакой авторизации не нужно** — ни Яндекса, ни Planfix.

## Как устроена загрузка

```
браузер ──1── POST /api/upload-url ──► наш сервер ──► Яндекс.Диск API (токен только здесь)
        ◄────── одноразовая ссылка uploader'а ◄──────
        ──2── PUT файла ────────────────────────────► uploader.yandex.net
        ──3── POST /api/upload-done ──► сервер сверяет размер файла на Диске
```

Ссылка от Яндекса подписанная и живёт 30 минут, при загрузке по ней токен не нужен —
поэтому 100-мегабайтные файлы **не проходят через наш сервер и через nginx**.

Прямой канал проверен на боевом аккаунте: браузер грузит файлы на
`uploader*.disk.yandex.net` без участия нашего сервера — CORS у Яндекса открыт.

На случай, если где-то (корпоративный прокси, старый браузер) кросс-доменный PUT
всё же запретят, форма молча переключается на резервный канал `PUT /api/upload-proxy` —
файл идёт через наш сервер потоком, без буферизации в память. Оба канала под тестом.

## Что происходит при отправке

1. На Диске создаётся папка `disk:/МИС-заявки/2026-08-27 ТП-2026-1234/` — в ней файлы и `заявка.txt`.
2. Папка публикуется по ссылке (`PUBLISH_FOLDER=true`), чтобы вложения открывались прямо из Planfix.
3. В Planfix уходит письмо:
   - тема: `[ТП-2026-1234] P0/P1 — критично · Медгород / ЭМК — Пропал редактор онкодиагнозов`
   - тело: заполненная карточка + ссылка на папку;
   - вложения до 10 МБ (суммарно до 20 МБ) кладутся прямо в письмо, крупные остаются на Диске;
   - `Reply-To` — почта заявителя, если он указал её в поле «Контакт».
4. Копия заявки пишется в `/var/lib/mis-form/tickets.jsonl`.

Если письмо не ушло — заявка всё равно сохранена, а заявителю показывается предупреждение
«скопируйте текст и продублируйте вручную».

## Токен Яндекс.Диска

Нужен один раз, от аккаунта, на диске которого будут лежать заявки.

1. [oauth.yandex.ru](https://oauth.yandex.ru/) → **Создать приложение**.
2. Платформа — «Веб-сервисы», Redirect URI — `https://oauth.yandex.ru/verification_code`.
3. В разделе **«Доступ к данным»** добавить все четыре права — каждое вводится
   в поле «Название доступа» и выбирается из подсказки:

   | Право | Зачем |
   |---|---|
   | `cloud_api:disk.write` | создавать папки заявок и заливать файлы |
   | `cloud_api:disk.read` | сверять размер залитого файла, прикладывать мелкие файлы к письму |
   | `cloud_api:disk.info` | показывать остаток места в `/api/health` |
   | `cloud_api:disk.app_folder` | не обязательно, мешать не будет |

   Без `disk.read` форма поднимется, но проверка размера и вложения в письме отвалятся.
4. **Redirect URI для веб-сервисов**: `https://oauth.yandex.ru/verification_code`
   (в интерфейсе есть галочка «подставить URL для отладки» — она вставляет именно его).
5. Создать приложение и скопировать **ClientID** с его страницы.
6. Открыть в браузере, подставив ClientID:
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENT_ID`
7. Подтвердить доступ — Яндекс покажет токен. Скопировать его в `YANDEX_DISK_TOKEN`.
   Токен показывают один раз, потом только выпускать заново.
8. Проверить настройку:

   ```bash
   npm run disk:check
   ```

Токен долгоживущий, но отзывается вместе с приложением. Держать только в `/etc/mis-form.env`.

## Почта для Planfix

1. Завести/взять почтовый ящик (например, на Яндекс 360): `mis-support@example.ru`.
2. В Яндекс ID → **Пароли приложений** → создать пароль для SMTP. Это `SMTP_PASS`
   (обычный пароль от почты не подойдёт).
3. В Planfix добавить адрес отправителя в контакты/сотрудники — иначе входящее письмо
   может не создать задачу.
4. Проверить связку:

   ```bash
   npm run mail:check           # пускает ли SMTP
   npm run mail:check -- --send # отправить тестовую заявку в Planfix
   ```

## Бот в MAX

Бот «Сопровождение МИЦ» задаёт те же вопросы, что и форма, и отдаёт в Planfix
**один пакет** на заявку.

### Почему нельзя просто дописать логику в бота

Planfix подключён напрямую к ключу бота — на токене висит его вебхук
`https://sensey.planfix.ru/endpoints/max?botId=391026515`. MAX отдаёт события
либо в вебхук, либо в поллинг, но не в оба сразу: пока подписка Planfix жива,
сторонний процесс не увидит ни одного сообщения. Поэтому бот работает
диспетчером — встаёт вебхуком вместо Planfix и решает, что пересылать:

```
MAX ──все события──► наш бот ──только готовый пакет──► вебхук Planfix
                        │
                        └── вопросы пользователю через API бота
```

Что при этом сохраняется:

- **Промежуточные ответы не уходят** в Planfix — ни один.
- **Заявка уходит одним сообщением** от имени пользователя, задача создаётся целиком.
- **Вложения** досылаются исходными событиями сразу за заявкой — падают в ту же задачу.
- **Переписка после заявки** проходит насквозь, чтобы ответы инженера работали.
- **При сбое** логики событие пересылается в Planfix как раньше — сообщение не теряется.

Всё перечисленное закреплено тестом на поддельных MAX и Planfix (`npm run bot:test`).

### Переключение и откат

```bash
npm run max:webhook                                    # что стоит сейчас
npm run max:webhook -- --set https://zayavka.dotcursor.ru/max-hook/СЕКРЕТ
npm run max:webhook -- --restore                       # вернуть Planfix напрямую
```

Перед переключением прежний адрес сохраняется в `max-webhook-backup.json`,
откат — одна команда. **Пока наш сервис не работает, заявки в Planfix не идут** —
переключаться стоит, когда бот уже поднят и отвечает.

### Проба без риска

Если не хотите трогать боевого бота, заведите второго у @MasterBot, положите его
токен в `MAX_TEST_BOT_TOKEN` и запустите `BOT_MODE=polling npm run bot`. Поллинг
не требует ни HTTPS, ни публичного адреса — бот отвечает в MAX сразу.

Диалог можно пройти и вовсе без MAX: `npm run dialog:demo`.

## Деплой рядом с dotcursor.ru (по IP)

На сервере 135.106.175.66 уже живут dotcursor.ru (Next.js на :3000) и статика onco
(она же отвечает на голый IP как `default_server`). Форма встаёт третьей, на путь
**`/zayavka/`**, ничего из существующего не трогая: установщик добавляет в блок
`default_server` одну строку `include snippets/mis-form.conf;`, делая перед этим
резервную копию и откатывая её, если `nginx -t` не пройдёт.

```bash
cd /var/www/dotcursor && git pull origin main
bash /var/www/dotcursor/mic/deploy/install-mis-form.sh
```

Первый запуск создаст `/etc/mis-form.env` и остановится — заполните в нём токен Диска
и пароль почты, запустите скрипт ещё раз. Дальше он сам проверит Диск и SMTP, поднимет
сервис на :3210 и настроит nginx. Итог: **http://135.106.175.66/zayavka/**

Повторный запуск того же скрипта = обновление (код, зависимости, рестарт).

⚠ По IP работает только HTTP — поля формы идут открытым текстом. Файлы при этом уходят
в Яндекс по HTTPS. Как только появится домен (годится поддомен, например
`zayavka.dotcursor.ru`), поставьте сертификат: `certbot --nginx -d zayavka.dotcursor.ru`.

## Деплой на отдельный домен

```bash
# код
mkdir -p /var/www/mis-form && chown deploy:deploy /var/www/mis-form
su - deploy -c 'git clone <repo> /var/www/mis-form && cd /var/www/mis-form && npm ci --omit=dev'

# настройки (заполнить по env.example)
cp /var/www/mis-form/env.example /etc/mis-form.env
chmod 600 /etc/mis-form.env && nano /etc/mis-form.env

# сервис
cp /var/www/mis-form/deploy/mis-form.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now mis-form
systemctl status mis-form

# nginx (подставить домен в конфиге)
cp /var/www/mis-form/deploy/nginx-mis-form.conf /etc/nginx/sites-available/mis-form.conf
ln -s /etc/nginx/sites-available/mis-form.conf /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

# HTTPS
certbot --nginx -d zayavka.example.ru
```

Проверка после деплоя:

```bash
curl -s https://zayavka.example.ru/api/health
```

Должно вернуться `{"ok":true,...}` — Диск отвечает и SMTP пускает.

## Настройки

Все — через переменные окружения, см. `env.example`. Значимые:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MAX_FILES` | `10` | сколько файлов на заявку |
| `MAX_FILE_MB` | `100` | предел на один файл |
| `PUBLISH_FOLDER` | `true` | публиковать ли папку заявки по ссылке |
| `RATE_PER_HOUR` | `20` | сколько заявок с одного IP в час |
| `DISK_ROOT` | `disk:/МИС-заявки` | корень на Диске |
| `TZ` | — | часовой пояс для дат и имён папок (`Asia/Yekaterinburg`) |

## Эксплуатация

- Логи сервиса: `journalctl -u mis-form -f`.
- Журнал заявок: `/var/lib/mis-form/tickets.jsonl` (по строке на заявку, включая `mailed`).
- **Брошенные папки.** Если заявитель приложил файлы и ушёл, не нажав «Отправить»,
  на Диске остаётся папка без `заявка.txt`. Их видно сортировкой по дате — чистить руками
  или скриптом раз в месяц.
- **Приватность.** При `PUBLISH_FOLDER=true` папку видит любой, у кого есть ссылка.
  В форме намеренно просят номер карты пациента, а не ФИО. Если политика клиники этого
  не допускает — поставить `PUBLISH_FOLDER=false`, тогда в письме будет только путь на Диске.
